# Phase 37.3: Code Review Report

**Reviewed:** 2026-10-28
**Depth:** standard
**Files Reviewed:** 18
**Status:** issues_found

## Summary

I reviewed the global search feature: the index, fold, highlight and wiki-strip helpers, the corpus hook, the combobox UI, the shortcut hook, the App/AppShell wiring, the list filter change, the locales, and the Rust diff since 200d3c5 (the `LIST_SEARCH_FIELDS` / `list_search_url` refactor). The Rust change is correct. Poll change detection still runs on the `fields=*all` detail fetch in `poll_engine.rs`, so adding `description` does not create change dots. The Zustand convention holds: `selectGroupIdsForIssue` returns a `null` fallback. No `brand-accent` usage was found, and `text-brand-muted` is used only on icons, never on text.

The main defect is in how keyboard selection relates to the debounced result set. Enter acts on stale results, so the jump-to-key flow can open the wrong ticket (CR-01). The poll-driven reset of the highlighted option causes a related problem (WR-01). The known observation is **confirmed**: the `<li role="option">` elements sit inside a `<div role="listbox">` (WR-02). I measured the wiki-markup stripper as quadratic on long single-line descriptions, and it runs before the 20k cap (WR-03).

## Critical Issues

### CR-01: Enter opens a hit from the stale (pre-debounce) result set, so fast typing opens the wrong ticket

**File:** `src/features/search/GlobalSearch.tsx:43-46, 133-137`
**Issue:** `result`, `hasHits` and `openHit` are all derived from `debounced`, which trails `query` by 150 ms. The Enter handler runs `openHit(active >= 0 ? active : 0)` against whatever the last debounced result was. Example: a user types `ABC-12` and presses Enter within 150 ms of the last keystroke. At that point `debounced === 'ABC-1'`, and `ABC-1` is an exact key match (rank 0), so the app navigates to **ABC-1** instead of ABC-12. Typing a key and pressing Enter is the main jump-to-ticket flow, so this sends the user to a different ticket with no warning. They may then triage it (dismiss, link, watch) thinking it is the one they asked for.
**Fix:** Flush the debounce on Enter before resolving the hit, or refuse Enter while the query and the debounced query differ:
```tsx
case 'Enter': {
  if (query !== debounced) {
    e.preventDefault();
    const fresh = searchTickets(items, query);
    setDebounced(query);
    const hit = fresh.hits[0];
    if (hit && onOpenTicket(hit.item.ticket.key)) { setOpen(false); setActive(-1); }
    return;
  }
  if (!hasHits) return;
  e.preventDefault();
  openHit(active >= 0 ? active : 0);
  return;
}
```
Add a test that types and presses Enter without advancing fake timers.

## Warnings

### WR-01: A background poll resets the highlighted option, so Enter then opens hit 0 instead of the highlighted row

**File:** `src/features/search/GlobalSearch.tsx:44, 50-52, 136`
**Issue:** `result` is memoized on `[items, debounced]`. `items` (useSearchCorpus.ts:87-114) is rebuilt whenever `tickets`, `triageMap`, `memberKeysByGroup` or `snap` change, which includes every poll and every triage action. Each rebuild produces a new `result`, and the effect at line 50 then sets `active` to -1. If a poll lands while the user is arrowing through results, the highlight disappears and Enter falls back to `openHit(0)`, which is a different ticket from the one they picked. In the render between the result change and the reset effect, `active` also points at an index in the *new* `hits` array, which may hold a different ticket.
**Fix:** Track the active option by ticket key, not by index. Reset it only when `debounced` changes. Resolve the key to an index at render time:
```tsx
const [activeKey, setActiveKey] = useState<string | null>(null);
useEffect(() => setActiveKey(null), [debounced]);
const active = activeKey ? result.hits.findIndex(h => h.item.ticket.key === activeKey) : -1;
```

### WR-02: `<li role="option">` rendered inside `<div role="listbox">` is invalid HTML (known observation confirmed)

**File:** `src/features/search/GlobalSearch.tsx:214`, `src/features/search/SearchResultRow.tsx:84-86`
**Issue:** An `<li>` is only valid as a child of `<ul>`, `<ol>` or `<menu>`. The listbox container is a `<div>`, so every option is an orphaned `<li>`. Browsers tolerate this, but it fails HTML validation, and some AT/browser pairs report implicit `listitem` semantics or list-structure errors. The biome suppression on line 85 says "listbox option inside ul per combobox pattern", which is false: there is no `ul`. The comment hides the problem from the linter.
**Fix:** Make the container a list and reset its default styling, or make the option a `div`:
```tsx
<ul id={listboxId} role="listbox" aria-label={t('search.listLabel')} className="list-none m-0 p-0">
```
Then correct the biome-ignore comment so it describes the real structure.

### WR-03: `stripWikiMarkup` is quadratic and runs on the uncapped raw description, which can freeze the main thread

**File:** `src/features/search/searchIndex.ts:46-47`, `src/features/search/wikiText.ts:9, 20`
**Issue:** `DESCRIPTION_INDEX_CAP` is applied *after* `stripWikiMarkup(rawDesc)`, so the regexes run over the full description. `WRAPPED` (`([*_+\-^~])(?=\S)([^\n]*?\S)\2`) scans to the end of the line from each candidate start position, and it runs twice. That makes it O(n²) per line. Measured in Node on a single line of repeated ` *a`: 15 kB took 97 ms, 30 kB took 397 ms, and 60 kB took 1561 ms. `buildEntry` runs synchronously on the UI thread on the first search after each poll, because the WeakMap cache is keyed by ticket object and polls replace the objects. One long single-line description (a pasted log or JSON blob) can therefore freeze the app on every keystroke after a poll. This is a hang, not just a slowdown, which is why it is not in the out-of-scope performance bucket.
**Fix:** Cap before stripping, and bound the wrapped-text span:
```ts
const rawDesc = typeof f.description === 'string' ? f.description.slice(0, DESCRIPTION_INDEX_CAP) : '';
const descDisplay = stripWikiMarkup(rawDesc);
// wikiText.ts
const WRAPPED = /(^|\s)([*_+\-^~])(?=\S)([^\n]{0,200}?\S)\2(?=\s|$|[.,;:!?)])/g;
```

## Info

### IN-01: Clear-button icon overrides the button's hover colour

**File:** `src/features/search/GlobalSearch.tsx:197-199`
**Issue:** The button sets `text-brand-text-secondary hover:text-brand-text`, but its only content, the `<X>`, sets its own `text-brand-muted`. The hover colour change therefore never shows, so the button gives no hover feedback. `brand-muted` (#8c8c92) on white is also only about 3.3:1.
**Fix:** Remove `text-brand-muted` from the `<X>` so it inherits `currentColor`.

### IN-02: Live region announces counts for a closed panel and on unrelated data changes

**File:** `src/features/search/GlobalSearch.tsx:57-64`
**Issue:** The announce effect depends on `[debounced, ready, total]` and ignores `open`. After the user opens a ticket or presses Escape, the query is kept. A later poll that changes `total`, or `ready` flipping during a snapshot reload, then makes a screen reader announce "N results" unprompted.
**Fix:** Return early when `!open`.

### IN-03: Opening from search during the copy flow is silently refused

**File:** `src/App.tsx:161-170`, `src/features/search/GlobalSearch.tsx:95-102`
**Issue:** `openTicketFromSearch` returns `false` while `copyPhase` is active. `GlobalSearch` then does nothing: there is no toast, no announcement, and the dropdown stays open. The user cannot tell why Enter or a click had no effect.
**Fix:** When `onOpenTicket` returns `false`, call `announce()` and show a toast (for example "Finish or cancel the copy first"), or hide the search region while the copy is active.

### IN-04: Ctrl/Cmd+K and Ctrl/Cmd+F are captured even while typing in other text fields

**File:** `src/features/search/shortcut.ts:27-36`
**Issue:** The window listener steals focus from any textarea or input, such as the JQL editor in Settings or comment fields in the detail view. In those fields, Ctrl+K often means "insert link" and Ctrl+F means find-in-field.
**Fix:** Skip the shortcut when `e.target` is a text field, contentEditable, or a textarea other than the search input, or document this as intentional in D-03.

### IN-05: Highlight/snippet folding differs from match folding for context-sensitive lowercasing

**File:** `src/features/search/normalize.ts:14-26`
**Issue:** `foldWithMap` lowercases one code point at a time, while `foldText` lowercases the whole string. These give different results for context-sensitive mappings such as Greek final sigma: `foldText('ΟΔΟΣ ')` returns `οδος ` (ending in final ς), but the per-char fold returns `οδοσ `. A ticket can then match but show no highlight, or `buildSnippet` can fall back to the first 80 characters. This is an edge case for SK/EN data.
**Fix:** Document the limitation, or fold the full string and build the map using `String.prototype.normalize` segment boundaries.

### IN-06: Missing priority renders an empty "Priority: " label

**File:** `src/features/search/SearchResultRow.tsx:38, 105-108`
**Issue:** When `priority` is absent, `priorityName` is `''`. The row then renders `title="Priority: "` and the same text in the sr-only span.
**Fix:** Render the priority span only when `priorityName` is set.
