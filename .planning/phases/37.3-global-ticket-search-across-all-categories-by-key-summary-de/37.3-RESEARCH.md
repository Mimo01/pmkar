### Locked Decisions
- **D-01:** Always-visible search field in the app header (`AppShell`), results in a dropdown panel under it. No separate Search page, no modal palette.

- **D-04:** Search runs **locally**, no network. Add `description` to the fetch/poll `fields=` list so description is stored with each ticket and its snapshot.
- **D-05:** Searchable fields: key, summary, description, assignee display name, labels, component names, fix version names, remembered linked Cloud key (`copiedKey`). Comments are **not** searched.
- **D-06:** Scope is every known ticket: current fetch results across all triage states, plus snapshot-only group members (Phase 32 durable snapshots). Each ticket appears once.
- **D-07:** **Silent upgrade:** first fetch after the update stores description without blue dots, change diffs or OS notifications. Description edits are never treated as a change from then on: description is search data only and kept out of the change-detection hash/diff, or handled equivalently.
- **D-08:** Result row: KEY · summary · priority icon / assignee, small neutral category badge (New / Dismissed / Linked / Watched), existing tinted group chips (no chip tooltips). When the match is only in description or another non-title field, a one-line snippet under the row.
- **D-09:** Selecting a result opens full `TicketDetailPage`. Back returns to the tab the user was on. Query is kept; refocusing search shows the same results.
- **D-10:** Top **20** results, then "Showing 20 of N, refine your search" when more.
- **D-11:** ARIA combobox keyboard pattern (same as assignee autocomplete): Arrow Up/Down, Enter opens, first Esc closes dropdown, second Esc clears text. Polite live region announces result count. WCAG AA in both themes.
- **D-12:** No-results: "No tickets match" plus hint listing what is searched. No remote search.
- **D-13:** Split query on whitespace. A ticket matches when **every** word is a case-insensitive substring of its searchable fields, any order.
- **D-14:** Ignore diacritics both directions (NFD normalize + strip combining marks).
- **D-15:** Ranking: exact key match, then key prefix, then summary hits, then description/other-field hits. Ties to most recently updated.
- **D-16:** Highlight matched text in key, summary, snippet. Search starts at **2 characters**, debounced about 150 ms.
- **D-17:** Every new string in EN and SK and passes i18n guards. Slovak says "tiket", never "úloha". Extend the WebView2 checklist with search box, shortcuts, dropdown.

## Summary

The feature is almost entirely frontend. Three codebase findings change how the plan should look compared to what CONTEXT.md assumed:

1. **The `fields=` list is not in `poll_engine.rs`.** The list-search URL exists in two places: `src-tauri/src/commands.rs:751` (user fetch, `fetch_tickets`) and `src-tauri/src/jira_client.rs:57` (`search_tickets`, used by the poll loop). Both need `description` appended. [VERIFIED: codebase grep]
2. **Snapshot hash/diff is computed over the detail response, not the list response.** `poll_engine::process_tickets` and the manual-fetch loop in `TicketListPage` both call `fetch_ticket_detail` (`fields=*all`) and hash that JSON in `snapshot_db::check_for_changes`. The detail JSON already contains `description`, and `WATCHED_FIELDS` in `snapshot_db.rs:20-29` already includes `("description", "/fields/description")`, so **description edits are currently treated as changes** (change dots, notifications). Adding `description` to the list `fields=` therefore causes **no** hash change and no dots: the "silent upgrade" half of D-07 is automatic. The "never a change from then on" half requires removing `description` from `WATCHED_FIELDS` (this is a user-visible behavior change versus today, see Open Question 1). Hash exclusion is not needed: with description out of `WATCHED_FIELDS`, a description-only edit changes the hash, `detect_changes` returns an empty list, the snapshot is re-stored, nothing is flagged. [VERIFIED: codebase read of snapshot_db.rs, poll_engine.rs, TicketListPage.tsx]
3. **Group snapshots are `JSON.stringify(listTicket)`** (`groupStore.ts:156,191`). Once the list fetch returns `description`, labels, components and fixVersions (labels/components/fixVersions are already in `fields=`, so they are already in stored snapshots at runtime even though `JiraTicket` does not type them), snapshots pick up description automatically via the existing `refreshSnapshots` after fetch. Tickets added from detail go through `detailToTicket`, which drops everything beyond the core fields, so those snapshots lack description until a live list refresh. Snapshot-only members whose snapshot predates this phase are searchable by key/summary/assignee only until the ticket reappears in a fetch. This is an accepted limitation to document, not a bug. [VERIFIED: codebase]

The recommended design is a pure TS search module (`src/features/search/`) with a WeakMap-cached normalized index per ticket object, a small Zustand `searchStore` that owns the query (because `AppShell` is remounted across `App.tsx` early-return branches, local component state would be lost on opening detail, contradicting D-09), and a custom ARIA combobox component that mirrors the assignee autocomplete in `TicketFilterBar`.

**Primary recommendation:** Build `searchIndex.ts` (normalize, index, match, rank, snippet, highlight ranges) as a pure tested module; a `searchStore` for query/open state; `GlobalSearch.tsx` mounted from `AppShell`; add `description` to both Rust `fields=` strings; drop `description` from `WATCHED_FIELDS`; widen `filterTickets` to key-or-summary using the same normalizer.

   |-- list issues (with description) ---------------------------> TicketListPage.handleFetch

   |                                                                   |   groupStore.refreshSnapshots -> issue_snapshot.ticket_json
   |                                                                   |
   |                                      get_group_members (per group, existing)  -> snapshot-only tickets
   |                                                                   |
   v                                                                   v
                                                      useSearchCorpus(): merge live + snapshot, dedupe by key,
                                                      attach category (from triageMap) + group ids (groupIdsByIssue)
                                                                       |

### Recommended Project Structure
```
src/features/search/
├── normalize.ts          # foldText(), foldWithMap() (diacritics + case, index map)
├── searchIndex.ts        # buildIndexEntry (WeakMap cache), searchTickets(), rank, snippet, highlightRanges
├── wikiText.ts           # stripWikiMarkup() for v2 description
├── searchStore.ts        # query, open flag, (zustand)
├── useSearchCorpus.ts    # merge live + group snapshots + category + groups
├── GlobalSearch.tsx      # combobox + listbox + live-region announce
├── SearchResultRow.tsx   # row (reuse PriorityIcon, UserAvatar, GroupChips)
├── Highlight.tsx         # <mark> rendering from ranges
└── __tests__/
```
`filterTickets` in `ticketListUtils.ts` imports `foldText` from `search/normalize.ts` (or normalize lives in `src/lib/` to avoid feature cross-import; planner's choice, keep it one module).

### Pattern 1: Query state in a Zustand store, not component state
**What:** `App.tsx` renders `<AppShell>` in separate early-return branches (wizard, settings, audit, detail, main) with different parent wrappers (`NavigationContext.Provider` in some, not in others). React will remount `AppShell` and everything under it when the branch changes, so a `useState` query inside `GlobalSearch` is lost the moment a result opens detail. D-09 ("query is kept") requires `searchStore` (`query`, `dismissed` flag). `LiveAnnouncer` already documents the same remount issue. [VERIFIED: App.tsx, LiveAnnouncer.tsx]
**When to use:** always for this component. Debounced/derived results can be local; only the raw query lives in the store. On remount, do not auto-open the dropdown; open on focus (UI-SPEC: "Focusing the field again with a kept query re-opens").

### Pattern 2: Precomputed normalized index cached by object identity
**What:** `const cache = new WeakMap<JiraTicket, IndexEntry>()` (same idiom as `ticketOrigins` in `ticketStore.ts`). `IndexEntry` holds folded strings: `key`, `summary`, `description`, `assignee`, `labels`, `components`, `fixVersions`, plus `updatedMs`. `copiedKey` is not on the ticket, so fold it per search from `triageMap[key]?.copiedKey` (cheap) or include it in the corpus item. `setTickets` replaces the array per fetch, so entries rebuild lazily after each fetch and old ones are garbage collected. For <=1000 tickets a full scan per debounced query is well under a few ms; no inverted index is needed. [ASSUMED: performance estimate, validate with a 1000-ticket test using realistic ~5 KB descriptions]
**Recommendation:** match each word against `[key, summary, assignee, labels, components, fixVersions, copiedKey, description]` joined with `\u0000` into one folded haystack for the AND test (fast), and keep the per-field strings for ranking and snippet source detection. Joining with a separator prevents a word from spanning two fields.

### Pattern 3: Corpus merge (live first, snapshot fallback)
Mirror `useGroupMembers`: live tickets from `useTicketStore.tickets`; for snapshot-only members, load via existing `useGroupStore.getState().getGroupMembers(groupId)` for each group, parse `ticketJson`, validate with the exported `isRenderableTicket`, key them in a map, add only keys not in live. No new Rust command is required (<= ~60 groups, cheap, Rust-side already scope-guarded). Reload when `snapshotRevision` or `memberKeysByGroup` changes. Do this lazily: load on first focus/typing, not at app start, and guard with a request token (cancel on stale), as `useGroupMembers` does. Keep one `Map<string, JiraTicket>` so each ticket appears once (D-06).
**Category:** derive from the triage predicates (`isNewCandidate`, `isNotMineCandidate`, `isLinkedCandidate`, `isWatchedCandidate`). Snapshot-only tickets have no live status guarantee; apply the same predicates against their stored status. Done tickets satisfy none of the predicates (see Open Question 2).
**Scope guard:** group data and `triageMap` are server-scoped (`resolve_scope`, `resetForServerSwitch`). Corpus must clear on server switch; build it from stores that already clear (`tickets`, `triageMap`) and reload group snapshots when `useGroupStore` hydrates. Do not cache the snapshot list across server switches.

### Pattern 4: AppShell integration
- Add an optional prop (e.g. `showSearch?: boolean`, or pass a `search` node) so the wizard branch (no connection, no data) renders no search. All post-setup branches in `App.tsx` (main, detail, settings, audit) pass it. UI-SPEC says "every screen including settings and ticket detail".
- Header is `flex items-center justify-between`. Place the search between brand mark and icon toolbar (UI-SPEC: centered). Wrap in `role="search"`. The dropdown is `absolute` relative to a `relative` wrapper; the header already has `relative`. Ensure `overflow-hidden` on the root (`h-screen ... overflow-hidden`) does not clip the panel: the panel hangs from the header inside the root, which is fine as long as it does not exceed the viewport; `max-h-[480px]` plus viewport clamp handles this.
- Opening a result: `GlobalSearch` gets an `onOpenTicket(key)` from `App.tsx` which must also `setShowSettings(false)`, `setShowAuditLog(false)`, reset `settingsInitialSection`, then `useTicketStore.getState().selectTicket(key)`. Calling only `selectTicket` from Settings or Audit does nothing visible because those branches return earlier than the detail branch. If detail is already showing and `copyPhase` is active (copy preview/result), `selectTicket` would change `detailTicketKey` but the copy pages stay on screen; either disable opening while `copyPhase !== 'idle'` or accept; recommend guard: ignore/disable selection while copy phase is `loading_preview|previewing|copying|result` and keep the dropdown open. [VERIFIED: App.tsx branches]
- Selecting the same key that is already `selectedTicketKey` does not retrigger the effect; handle by `selectTicket(null)` then key, or navigate directly. From the detail page itself the user may search another ticket: `TicketDetailPage` takes `issueKey` prop with effect deps `[issueKey, baseUrl]` so a key change refetches; verify with a test.

### Pattern 5: Result row and highlight
Build on `PriorityIcon`, `UserAvatar`, `GroupChips`, existing tab label keys (`nav.new`, `nav.notMine`, `nav.linked`, `nav.watched`; note the "Dismissed" badge text must come from the label users see in the Dismissed tab, which is `nav.notMine` in SK "Zamietnuté"; confirm EN label with `en.json`). Highlight renders `<mark>` segments from index ranges computed against the original string (see Code Examples). Rows are `role="option"` with stable ids; the input carries `aria-activedescendant`.

### Pattern 6: Ranking
Score per ticket (lower is better, then `updatedMs` desc): 0 = folded key equals the full folded query (single word or the whole trimmed query); 1 = key startsWith first word; 2 = all words found within key+summary; 3 = otherwise (description/other fields). Do the sort on the matched set only, then slice 20 and keep `total`. A ticket with a summary hit must outrank one with description-only hits even when `updated` is newer (D-15). Typing `MYPROJ-12` finds the linked source via `copiedKey` (category 3; consider scoring a `copiedKey` exact match as 0 or 1 since users type it as an identifier; planner's discretion, flag to user in plan).

### Anti-Patterns to Avoid
- **Local `useState` for the query** (lost on branch remount, see Pattern 1).
- **Re-normalizing every ticket on every keystroke** (cache folded strings; only fold the query).
- **Computing highlight/snippet for all matches** (only for the 20 rendered rows).
- **Single-word fold with `toLowerCase` only** (breaks D-14).
- **Returning `?? []` from a Zustand selector** (infinite loop, project memory). Use `null` fallbacks.
- **Adding DnD, hover-revealed row actions, restore buttons, or `text-brand-muted` / `brand-accent` styling** (project feedback memories, UI-SPEC).
- **Passing the raw description object to the index.** v2 description is a string, but a ticket originating from a Cloud/ADF source or a malformed snapshot may carry an object or null; coerce with `typeof === 'string'` and ignore otherwise.

## Common Pitfalls

### Pitfall 1: Assuming description change is silent by default
**What goes wrong:** Description edits currently produce change dots and notifications because `WATCHED_FIELDS` includes it. D-07 says they must not.
**How to avoid:** Remove the `("description", ...)` tuple from `WATCHED_FIELDS`; update/replace Rust tests that assert a description change (grep `description` in `snapshot_db.rs` tests around line 393 and `poll_engine`/notification tests); add a test that a description-only edit yields `detect_changes == []`. Do **not** touch `compute_hash` (no need; stored hashes then simply differ once and re-store silently). Verify `notification_dispatcher` and any TS field-label maps do not require the `description` key.
**Warning signs:** blue dots on many tickets after the first fetch following the update.

### Pitfall 2: Esc conflicts with `TicketDetailPage`
**What goes wrong:** `TicketDetailPage` has a `document` keydown listener that calls `onBack()` on Escape unless `e.defaultPrevented` or the target is inside `[role="alertdialog"]`. Pressing Esc in the header search while on a detail page would leave the page.
**How to avoid:** In the combobox's React `onKeyDown`, call `e.preventDefault()` for Escape whenever it is handled (dropdown open or text non-empty). React 17+ attaches handlers at the root, which runs before the `document` listener, so `defaultPrevented` is already true. Add a test: Esc in the search input on detail page does not call `onBack`. When the dropdown is closed and the text is empty, let Esc propagate (so Esc in an empty search on detail still goes back), or always swallow; choose and document. Same concern for `TicketDetailPanel`'s listener.

### Pitfall 3: Ctrl+F and the WebView2 find bar
**What goes wrong:** WebView2 processes browser accelerator keys (Ctrl+F find, F5, etc.) in the host and, per community reports, possibly before page JS can `preventDefault`. Tauri 2.10.3 does not expose `AreBrowserAcceleratorKeysEnabled`; a PR to expose `browser_accelerator_keys` (tauri-apps/tauri#16397, issue #16306) was open as of the search and I could not confirm a merge. [CITED: github.com/tauri-apps/tauri/issues/16306; learn.microsoft.com ICoreWebView2Settings3] The existing code already does `preventDefault` on F5 in `TicketListPage`, which suggests JS interception works for at least some accelerators on this setup, but this is unverified for Ctrl+F. [ASSUMED]
**How to avoid:** Implement the handler with `preventDefault()` on `keydown` for Ctrl/Cmd+F and Ctrl/Cmd+K. Make the WebView2 checklist item explicit ("Ctrl+F does not open the browser find bar on Windows"). If it fails, fallbacks in order: drop Ctrl+F and keep Ctrl+K only (D-03 amendment, user decision), or upgrade Tauri once the accelerator option ships. Do not add a Rust `with_webview` hack in this phase.
**Warning signs:** find bar appears over the app on Windows only; macOS (WKWebView) unaffected.

### Pitfall 4: AppShell remount and branch navigation
See Pattern 1 and Pattern 4 (selecting from Settings/Audit/copy pages; selecting the same key twice).

### Pitfall 5: Diacritics folding changes string length
`'Chyba prihlásenia'.normalize('NFD')` inserts combining marks, so indexes in the folded string do not map to the original; naive `indexOf` on folded text then slicing the original produces wrong highlights/snippets. Also `'İ'.toLowerCase()` expands to two code units. **How to avoid:** `foldWithMap` (Code Examples) folds per code point and records the original index for each output unit; use it only for display strings (key, summary, snippet source). For the match-only test use plain `foldText`. Characters that do not decompose (ł, đ, ø, ß) are not folded; acceptable, document in tests.

### Pitfall 6: Modal detection and "don't hijack typing"
Shortcuts must not fire while a modal is open: Radix Dialog content renders `role="dialog"` (or `alertdialog`) with `data-state="open"`. Check `document.querySelector('[role="dialog"][data-state="open"], [role="alertdialog"][data-state="open"]')` (also `aria-modal="true"`) at keydown time; if found, do nothing and do not `preventDefault`. UI-SPEC says K/F focus search even when focus is in another text input (excluding modals); only plain keys must not be intercepted. Require `(ctrlKey || metaKey) && !altKey && !shiftKey` so Ctrl+Shift+F and Alt combos are untouched. Use `e.key.toLowerCase()` (Caps Lock, Slovak layout fine since K/F are Latin). Note AppShell has no existing window-level key handler (only the nav arrow-key handler on the `<nav>`), contrary to the CONTEXT note; add a new `useEffect` window listener in `GlobalSearch`, not in `AppShell`'s nav handler.

### Pitfall 7: Large descriptions and memory/snapshot size
1000 tickets x description size is held in memory and re-serialized into `issue_snapshot` for group members. Jira server descriptions are typically a few KB but can be 100 KB+. Mitigations (discretion): cap the stored searchable description (e.g. truncate to first ~20 KB) in a `slimTicketForSnapshot()` applied before `JSON.stringify` in `groupStore` (both call sites at lines 156 and 191), and truncate when building the index. Do not alter `isRenderableTicket` (description is optional).

### Pitfall 8: Types
`JiraTicket.fields` has no `description`, `labels`, `components`, `fixVersions`. Add optional `description?: string | null; labels?: string[]; components?: JiraComponent[]; fixVersions?: JiraFixVersion[]` (types already exist). `isRenderableTicket` stays unchanged since these are optional. Cloud-origin tickets are not in this list (server only), so ADF handling is unnecessary beyond the `typeof string` guard.

### Fold + index-mapped fold
```typescript
// Source: MDN String.prototype.normalize; project decision D-14
const MARKS = /\p{M}/gu;

/** Fold for matching only: NFD, drop combining marks, lowercase. */
export function foldText(s: string): string {
  return s.normalize('NFD').replace(MARKS, '').toLowerCase();
}

/** Fold with a map: folded[i] came from original[map[i]]. For highlight and snippet only. */
export function foldWithMap(s: string): { folded: string; map: number[] } {
  let folded = '';
  const map: number[] = [];
  let i = 0;
  for (const ch of s) {
    const f = ch.normalize('NFD').replace(MARKS, '').toLowerCase();
    for (let k = 0; k < f.length; k++) map.push(i);
    folded += f;
    i += ch.length;
  }
  map.push(s.length); // sentinel for end offsets
  return { folded, map };
}

/** Ranges in the ORIGINAL string covering every occurrence of any query word. */
export function highlightRanges(original: string, words: readonly string[]): [number, number][] {
  const { folded, map } = foldWithMap(original);
  const ranges: [number, number][] = [];
  for (const w of words) {
    let from = 0;
    for (;;) {
      const at = folded.indexOf(w, from);
      if (at < 0) break;
      ranges.push([map[at], map[at + w.length]]);
      from = at + Math.max(w.length, 1);
    }
  }
  return mergeRanges(ranges); // sort + merge overlaps (implement and unit test)
}
```
