# Phase 37.3: Global ticket search - Context

**Gathered:** 2026-10-28
**Status:** Ready for planning

<domain>
## Phase Boundary

One search across every ticket the app knows about: New, Dismissed (`ignored`), Linked (`copied`), Watched, and every group member, including snapshot-only members. It matches key, summary, description and a few other local fields, and runs in the app on locally stored data. It lives in an always-visible header search box with a results dropdown. Selecting a result opens ticket detail. The per-tab filter stays, and it now matches summary as well as key.

Not in scope: searching the customer Jira for tickets the app doesn't know yet (remote JQL), searching comments, and any new triage/group actions from search results.

</domain>

<decisions>
## Implementation Decisions

### Where search lives
- **D-01:** An always-visible search field in the app header (`AppShell`), with the results in a dropdown panel under it. No separate Search page and no modal palette.
- **D-02:** The per-tab `TicketFilterBar` text filter stays on every tab, but `filterTickets` now matches **key or summary**. Update the placeholder/aria strings in EN and SK ("Filter by key or summary…"). The assignee filter and sort are unchanged.
- **D-03:** **Ctrl/Cmd+K** and **Ctrl/Cmd+F** focus the global search. Only modifier shortcuts, no single-key shortcuts. Show a shortcut hint inside the field (e.g. `⌘K` / `Ctrl K` per platform). The shortcuts must not fire while a modal dialog is open and must not take over typing in other inputs beyond focusing search.

### Searchable fields & data
- **D-04:** Search runs **locally** and needs no network. Add `description` to the fetch/poll `fields=` list (`poll_engine.rs` search URL, plus the TicketListPage fetch path if it's separate) so description is stored with each ticket and its snapshot.
- **D-05:** Searchable fields: key, summary, description, assignee display name, labels, component names, fix version names, and the remembered linked Cloud key (`copiedKey` from triage). Comments are **not** searched.
- **D-06:** Scope is every known ticket: current fetch results across all triage states, plus snapshot-only group members (Phase 32 durable snapshots). Each ticket appears once.
- **D-07:** **Silent upgrade:** the first fetch after the update stores description without blue dots, change diffs or OS notifications. Description edits are also never treated as a change from then on: description is search data only and is kept out of the change-detection hash/diff, or handled in an equivalent way.

### Results & opening a hit
- **D-08:** A result row shows KEY · summary · priority icon / assignee, plus a small neutral category badge (New / Dismissed / Linked / Watched) and the existing tinted group chips (no chip tooltips, per the chip style rules). When the match is only in description or another non-title field, a one-line snippet around the match appears under the row.
- **D-09:** Selecting a result opens the full `TicketDetailPage`. Back returns to the tab the user was on. The query is kept, so refocusing search shows the same results.
- **D-10:** Show the top **20** results, then a line like "Showing 20 of N, refine your search" when there are more.
- **D-11:** Keyboard follows the **ARIA combobox** pattern, the same as the assignee autocomplete: Arrow Up/Down moves the active option, Enter opens it, the first Esc closes the dropdown and a second Esc clears the text. A polite live region announces the result count. WCAG AA contrast in both themes.
- **D-12:** No-results state: a "No tickets match" message plus a hint listing what is searched (key, summary, description, assignee, labels…). It offers no remote search.

### Matching rules
- **D-13:** Split the query on whitespace. A ticket matches when **every** word appears as a case-insensitive substring somewhere in its searchable fields, in any order.
- **D-14:** Ignore diacritics in both directions (NFD normalize + strip combining marks), so `prihlasenia` ↔ `prihlásenia`.
- **D-15:** Ranking: exact key match first, then key prefix, then summary hits, then description and other-field hits. Ties go to the most recently updated.
- **D-16:** Highlight matched text in key, summary and snippet. Search starts at **2 characters**, debounced about 150 ms.

### i18n / a11y
- **D-17:** Every new string exists in EN and SK and passes the i18n guards. Slovak says "tiket", never "úloha", for issues. Extend the WebView2 checklist with the search box, shortcuts and dropdown.

### Claude's Discretion
- Index structure (precomputed normalized strings vs. scanning on each query), and how description is held in memory and in snapshots.
- How v2 wiki-markup description becomes searchable plain text (stripping markup is fine).
- Snippet length, highlight styling, header field width, and the exact i18n key names.
- How to keep description out of change detection (D-07) while still storing it.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- The `TicketFilterBar` assignee combobox: keyboard/listbox/aria pattern to reuse for the results dropdown.
- `GroupChips`, `PriorityIcon`, `UserAvatar`, `TriageIndicator`: result row parts.
- Category predicates (`isNewCandidate`, `isNotMineCandidate`, `isLinkedCandidate`, Watched equivalent) that derive the category badge.
- `LiveAnnouncer`: result-count announcements.

### Established Patterns
- Today search is key-only and per page, client-side over `ticketStore.tickets`.
- Snapshots use a SHA-256 hash over `response_json`. Adding a field changes the hash, hence D-07.
- Group snapshot rows deliberately drop large text (`detailToTicket.ts`).

### Integration Points
- The AppShell header, the global keydown handling in AppShell (it already ignores modifier combos, so adjust for Ctrl/Cmd+K/F), App.tsx detail navigation, the fetch/poll field lists in Rust and TS, the mock server fixtures (add descriptions for test data), and the EN/SK locale files.

</code_context>
