<objective>
Close the stale-ticket-list half of review finding CR-01 (new): server A's tickets must never stay or become the live list while server B is the active connection.

Purpose: today `setTickets` runs unconditionally after the fetch await, and nothing clears the list when the server changes. Two consequences follow:
1. B's group views render A's live data for colliding keys, because `useGroupMembers` prefers live over snapshot.
2. The list feeds A's tickets into "Add to group", which is the overwrite path. Plan 32-10 adds the Rust veto there.

This plan clears the list on a baseUrl change and refuses to apply results from a fetch whose server changed mid-flight.

Output: `resetForServerSwitch` plus a connection subscription in ticketStore, a gated setTickets in both handleFetch paths, and vitest coverage.

Deliberate choice (documented deviation from the review's literal wording): the review suggests gating setTickets with the full-signature `isFetchStillCurrent()`. This plan gates setTickets on server identity only (baseUrl and username, compared to the `serverConn` captured at fetch start) for three reasons:
- CR-01 is a cross-server problem.
- Gating on the full signature would throw away a valid same-server fetch whenever the user changes the preset or filter while it is loading. The in-flight lock means no replacement fetch would run.
- It would break the locked test 'preset changed mid-flight stores the fetch-start signature'.

Hint safety for a filter change is already guaranteed, because the stored fetch-start signature no longer matches. Snapshot refresh keeps its stricter full-signature `isFetchStillCurrent()` gate from 32-08, unchanged.
</objective>

## Trust Boundaries

| Boundary | Description |

| async Jira fetch result -> live ticket store | Data fetched from server A arrives after the active connection may have become server B |
| live ticket store -> group views and add path | The live list is preferred over snapshots in group views and is the source of tickets for add_issues_to_group |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-36 | Tampering (another server's data shown as live and fed to add) | ticketStore after a server switch | mitigate | useConnectionStore.subscribe calls resetForServerSwitch when baseUrl changes from a non-null value |
| T-32-37 | Tampering (mid-flight result applied to the new server) | TicketListPage.handleFetch setTickets | mitigate | isSameServerAsFetch() checked before setTickets on both paths; on mismatch discardStaleResult() and return |
| T-32-38 | Information disclosure (old server's ticket detail stays open) | selectedTicketKey | mitigate | resetForServerSwitch clears selectedTicketKey |
| T-32-39 | Denial (user's fetch discarded after switching server) | handleFetch | accept | Correct behavior: results belong to an inactive server. The in-flight lock is released, so the user can fetch again immediately |
</threat_model>
