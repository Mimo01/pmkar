<objective>
Close the add-path half of review finding CR-01 (new): `add_issues_to_group` must never upsert one server's ticket JSON into another server's scope.

Purpose: `add_members` runs `INSERT ... ON CONFLICT(scope, issue_key) DO UPDATE SET ticket_json = excluded.ticket_json`. If the frontend still holds server A's ticket while Rust's connection scope is server B, adding that ticket overwrites B's snapshot of a colliding key in every B group. This plan gives the add path the same expected-scope veto that 32-08 added to refresh. Because this is a user action, a mismatch returns a distinct, translated error instead of a silent no-op.

Output: new `ScopeMismatch` error code (Rust and TS), a Rust veto plus cargo tests, `groupStore.addToGroup` sending `expectedBaseUrl`, `membershipErrorKey` mapping, en/sk copy, vitest coverage.

Design choices (Claude's discretion, per the orchestrator's "choose NoScope or new code"):
- Use a NEW code `scope_mismatch`. The existing `groups.error.noScope` copy ("No project scope is selected. Choose one in Settings...") would mislead the user here.
- `addToGroup` reads the expected base URL from `useConnectionStore.getState().serverConnection?.baseUrl ?? ''` at invoke time. All three production callers (membershipActions.addIssuesWithFeedback, GroupPicker, DetailGroupsRow) go through `addToGroup`, so this covers them without changing their signatures. Plan 32-11 guarantees the ticket list is cleared when the frontend base URL changes, so list tickets always belong to the frontend's current base URL. This veto catches frontend/Rust drift (for example, `set_connection_meta` still in flight or swallowed by SettingsPage's `.catch(() => {})`).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| in-memory ticket data -> persisted SQLite snapshots (add path) | Ticket JSON held by the frontend may come from a server other than the one Rust currently scopes to |
| JS -> Rust IPC (add_issues_to_group) | expectedBaseUrl is caller-supplied; Rust uses it only as a narrowing check |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-32 | Tampering (cross-scope snapshot overwrite via upsert) | add_issues_to_group_inner | mitigate | Compare normalize_scope(expected_base_url) to require_scope(); on mismatch return Err(ScopeMismatch) before locking groups_db, so nothing is written |
| T-32-33 | Elevation (caller chooses the write scope) | add_issues_to_group | mitigate | Write scope is still derived in Rust from connection meta; expectedBaseUrl can only veto |
| T-32-34 | Repudiation (silent failure hides the veto) | groupStore.addToGroup / membershipErrorKey | mitigate | A distinct scope_mismatch code is mapped to translated copy and shown by the toast or inline error; it is not mapped to internal and not returned as Ok(0) |
| T-32-35 | Denial (legitimate add blocked by frontend/Rust URL drift) | add path | accept | The user gets an actionable message (fetch again). The drift itself is the condition under which writing would be unsafe |
</threat_model>
