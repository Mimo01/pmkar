<objective>
Close review finding WR-01, which the verifier said should be fixed: the single missing-member Remove confirm must recheck "still missing" at confirm time, the same way the bulk path does.

Purpose: GDUR-05 and the T-32-23 race guard say a member that came back is never removed. The bulk paths (GroupViewPage Remove all, RemoveMissingPopover) recheck through readMissingKeysNow. The per-card path calls removeMissingMember unconditionally. The guard goes inside `removeMissingMember`, its only caller is the GroupViewPage per-card confirm, so the call site stays unchanged and the guard gets a direct unit test. A component-level race is hard to reproduce, because the popover unmounts when the card stops being missing.
Output: the guarded removeMissingMember and its unit tests.

Deferred review items (not in this plan, recorded for the SUMMARY):
- WR-02 (bulk count versus visible heading). This is a product decision. The existing test "Remove all missing uses the group-wide count and one call" encodes the current group-wide behavior on purpose, so it is not a trivial fix.
- WR-03 (ConfirmRemovePopover closes on failure). It changes popover open, focus and unmount timing across 3 confirm surfaces. It is not trivially low-risk.
- WR-04 (one invalid item aborts the batch refresh). groupStore.refreshSnapshots already sends only keys that are current group members, and those keys were validated on add, so the risk is low. Changing Rust batch semantics is not trivial.
- IN-01..IN-03 (info level).
