## Spacing Scale

Declared values (multiples of 4 only):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps (`gap-1`), tight inline padding |
| sm | 8px | Compact element spacing (`gap-2`, `p-2`) |
| md | 16px | Default element spacing (`px-4`, `gap-4`) |
| lg | 24px | Section padding (`py-6`, `gap-6`) |
| xl | 32px | Layout gaps (`py-8`) |
| 2xl | 48px | Major section breaks (`py-12`) |
| 3xl | 64px | Page-level spacing (`py-16`) |

Exceptions:

- Touch targets for icon-only buttons: 28px (`w-7 h-7`) — established by gear icon button in AppShell; do not change
- Interactive element vertical padding: `py-2.5` (10px) — **inherited deviation from the 4-point grid.** This value is present throughout the entire codebase across all prior phases: `ConnectionForm.tsx` input fields, `SecretInput.tsx` inputs, `SettingsPage.tsx` JQL textarea and list items, `AppShell.tsx` header, `CopyPreviewModal.tsx` header bar, `SummaryStep.tsx` buttons, `SetupWizard.tsx` buttons, `TicketTable.tsx` table headers, `IgnoredTicketsPage.tsx` table headers, `AuditLogPage.tsx` table headers, and `TestResult.tsx` status rows. It is the project-wide vertical padding for interactive elements at compact density. **The language dropdown must use `py-2.5` to match every other form control in the app.** Changing only the language dropdown to `py-3` would make it visually taller than all other inputs — that would be the inconsistency, not the deviation.

**Source:** Extracted from AppShell (`px-5 py-2.5`), SettingsPage (`px-6 py-8`, `gap-2`, `py-6`, `py-16`), ConnectionForm, SecretInput, IgnoredTicketsPage, AuditLogPage, TicketTable, CopyPreviewModal, SetupWizard, SummaryStep, TestResult.

## Component Inventory

New UI elements introduced in this phase:

### 1. LanguageSection (added to SettingsPage)

Placement: Below ThemeSection (last item in the `space-y-8` div), not above it — keeps language as a secondary preference below appearance.

Structure:
```
<section>
  <h2 class="text-xs font-semibold text-brand-muted uppercase tracking-wider mb-3">
    {t('settings.language')}
  </h2>
  <select
    class="w-full rounded-lg border border-brand-border bg-brand-surface text-brand-text px-3 py-2.5 text-sm focus:outline-none focus:border-brand/50 focus:ring-1 focus:ring-brand/20 transition-colors duration-200"
  >
    <option value="en">{t('settings.language.english')}</option>
    <option value="sk">{t('settings.language.slovak')}</option>
  </select>
</section>
```

The `py-2.5` in the select class string is the project-wide inherited deviation — identical to every other form input in the codebase. Do not change it.

No custom dropdown widget. Use a native `<select>` element. This is consistent with the app's existing pattern of using native form controls (textarea, input) without custom wrappers.

### 2. Language Provider in App.tsx

No visible UI change. The `I18nextProvider` wraps the existing component tree transparently. No loading spinner, no language gate — the existing `hydrated` guard already prevents any render before hydration completes (including language hydration per RESEARCH.md Pattern 3).

### 3. Modified: AppShell NAV_TABS

The `NAV_TABS` constant moves from module-level to inside the `AppShell` component function body to enable `useTranslation()`. No visual change — same two tabs, same layout. The change is purely to enable translated labels.

### 4. Modified: All components with visible text

All ~20 component files get string extraction. No visual changes — only hardcoded string literals replaced with `t('key')` calls. Pixel-perfect visual fidelity is required; if a component looks different after string extraction, that is a bug.

## Interaction Contract

### Language Switch Behavior

1. User opens Settings page (gear icon in AppShell header)
2. User scrolls to "Language" section (below "Appearance")
3. User selects a language from the native `<select>` dropdown
4. Language changes immediately — all visible strings update in the same React render cycle (react-i18next re-renders all consumers automatically via `i18n.changeLanguage()`)
5. No page reload, no confirmation, no toast notification — immediate update is the feedback
6. Preference persists via Tauri SQLite `app_config` table — survives app restart

### No Language Indicator in Header

Per D-02, the AppShell header does not show the active language. The header shows only the `pmkar` logotype and the gear icon. This is a locked decision — do not add a language badge or flag icon to the header.

### First Launch Detection

On first launch, the app detects OS locale via Rust `get_os_locale` command. If locale starts with `"sk"`, app starts in Slovak; otherwise English. This detection is transparent — the user sees the correct language on first render with no flash of wrong language (achieved by including `hydrateLanguage()` in App.tsx's existing `Promise.all` hydration guard).
