# Phase 37.2: Code Review Report

**Reviewed:** 2026-10-21
**Depth:** standard
**Files Reviewed:** 20
**Status:** issues_found

## Summary

The Watched state is wired consistently across the Rust validation, the SQLite CHECK migration (4- and 5-value shapes), the predicates, the tab and group badge, the detail actions and the locale files. SK/EN key parity holds. I found no blockers. The issues below are robustness and consistency gaps.

## Warnings

### WR-01: CHECK-constraint migration is not atomic on failure and swallows the detection error

**File:** `src-tauri/src/triage_db.rs:125-140` (SQL at 50-70)
**Issue:** `MIGRATE_TRIAGE_CHECK_WATCHED` runs through `execute_batch` with its own `BEGIN/COMMIT`. If any statement fails (for example `INSERT ... SELECT` on an unexpected legacy column set, or a leftover `triage_state_new` from an earlier aborted run), the batch stops with the transaction still open. The connection is then used for later statements in that state, and nothing issues a ROLLBACK. Separately, `query_row(...).ok().flatten()` converts any SQL error into "no table", so the migration is silently skipped and `set_triage('watched')` later fails with a CHECK violation. This is the third widening of the constraint, so the risk grows each time.
**Fix:** Run the migration with `conn.unchecked_transaction()` (or `Transaction`) instead of embedded BEGIN/COMMIT, so it rolls back on drop. Add `DROP TABLE IF EXISTS triage_state_new;` before the CREATE. Propagate the `query_row` error instead of `.ok()`.

### WR-02: Restore from Watched drops a remembered link to `seen` instead of relinking, which is inconsistent with Dismissed

**File:** `src/features/tickets/triageActions.ts:183-203`
**Issue:** `restoreTicket` relinks only when `state === 'ignored' && copiedKey`. A Watched ticket that came from Linked (copiedKey kept) is restored to `seen`, and the key stays as a stale hint. The user who parked a Linked ticket in Watched and clicks Restore lands in New, not Linked. The detail view also labels the button "Restore" (`watched.restore`) with a separate "Restore link to KEY" primary button next to it. If this is intended (D-decisions), the row-level Restore in `WatchedTicketsPage` and `GroupViewPage` gives no hint of the difference. If it is not, the Linked round trip is lossy.
**Fix:** Confirm the intended behaviour. If Restore should return to the previous bucket, extend the condition to `(current?.state === 'ignored' || current?.state === 'watched') && current.copiedKey`. Otherwise document it and clarify the label copy.

### WR-03: Undo toast for Dismissed -> Watched hard-codes the prior state and the stale check is state-only

**File:** `src/features/tickets/triageActions.ts:139-174`
**Issue:** `undoWatch` guards only on `state === 'watched'`. If the user watches, then restores to `seen`, then watches again within the toast window, an older toast (same id, so it is replaced) is fine. A Watched ticket that was set from another path, such as a bulk action or another detail view, can still be undone by a toast belonging to an earlier action and reverted to `ignored`. The `priorState === 'copied'` early return is dead code today, because `watchTicket` always passes `'ignored'`. It silently no-ops if someone later passes `'copied'`, with no feedback.
**Fix:** Drop the unreachable `copied` branch or surface an error. Narrow the parameter type to `Exclude<TriageState, 'copied'>`. Optionally compare `lastUpdated` or a token captured at watch time.

## Info

### IN-01: Shadowed `t` in `WatchedTicketsPage`

**File:** `src/features/tickets/WatchedTicketsPage.tsx:32, 44, 47`
**Issue:** Arrow params named `t` shadow the `t` from `useTranslation()`. It is harmless today, but a later edit that calls `t('...')` inside those callbacks would break. The same pattern appears in `useCoreTabCounts.ts:14`.
**Fix:** Rename the params to `ticket`.

### IN-02: Filtered-to-empty Watched list renders a blank area

**File:** `src/features/tickets/WatchedTicketsPage.tsx:76-100`
**Issue:** The empty state shows only when `watchedTickets.length === 0`. When search or assignee filters yield zero rows, the list is blank except for the result count. This matches `IgnoredTicketsPage`, so it is a consistency note, not a regression.
**Fix:** Optionally add a "no matches" message for `sorted.length === 0 && watchedTickets.length > 0`.
