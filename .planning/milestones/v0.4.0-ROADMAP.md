# Milestone v0.4.0: Configurable Field Mapping

**Status:** ✅ SHIPPED 2026-04-29
**Phases:** 17-23
**Total Plans:** 28

## Overview

Replace the hardcoded core-field copy logic with a fully user-configurable, field-type-aware mapping engine that bridges Jira Server v2 → Cloud v3 cleanly, supports custom fields, gates on required-field completeness, and surfaces every mapping decision in the audit log. Comments, attachments, worklogs, sub-tasks, summary, and the origin remote link stay hardcoded inside the existing copy pipeline; the mapping engine governs core fields and custom fields only.

## Milestone Summary

**Key Decisions:**

- db-per-concern pattern extended to mapping.db (separate from triage.db / snapshot.db / audit.db)
- Global mapping scope (one mapping for app) — simpler than per-project-pair; per-copy overrides give flexibility
- Person picker always visible with email-match pre-fill — avoids silent assignment failures
- Block copy on unmapped required target fields — prevents Jira Cloud rejection mid-pipeline
- Target issue type chosen at copy time — source/target type semantics differ; auto-match too brittle
- CopyContext seam at copy_ticket_v2 — clean boundary for helper extraction
- Hash-based audit redaction by default, verbose opt-in — balances auditability with PII protection

**Issues Resolved:**

- INT-02 (v0.1.0 known gap): Hardcoded `MYPROJ` cloud project key — fully parameterized in Phase 23
- B-01: UNIQUE INDEX on target_field_id blocking gap resolution for mandatory fields
- B-05: User prefill excluded from PREFILLABLE_KINDS — expanded to user and wiki_to_adf transformers
