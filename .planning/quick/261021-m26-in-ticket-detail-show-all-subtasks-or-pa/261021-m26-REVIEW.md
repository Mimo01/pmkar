## Summary

No secrets, injection, or dangerous-function patterns were found. The Rust search change only extends a static `fields=` list. The Jira search response is passed through as raw `serde_json::Value`, so `subtasks` and `parent` reach the frontend without struct changes. Missing and optional fields are handled with `?.` and `?? []`. The issues below are robustness and maintainability problems.

## Warnings

### WR-01: Relation rows on the card are an unbounded list

**File:** `src/features/tickets/TicketCard.tsx:154-182`
**Issue:** Every subtask is rendered on every card with no cap. A ticket with dozens of subtasks makes one row very tall, and this is in list views that render many cards. The user asked for "all" subtasks, but only in the ticket detail. The card has no truncation or "+N more" affordance.
**Fix:** Cap the card at about 5 rows, e.g. `subtasks.slice(0, 5)` plus a "+N" label. Keep the full list in `OverviewTab`.

### WR-02: Related-issue rows render an empty summary and no fallback when the data is partial

**File:** `src/features/tickets/RelatedTicketRow.tsx:22-27`
**Issue:** `JiraRelatedIssue.fields` is optional, and the component renders `''` when the summary is missing. Parent or subtask references that lack `fields` (for example from permission-restricted issues or older cached tickets) show only a bare key chip. The truncating span stays in the layout as an empty flex child. This is not a crash, but there is no visual or accessible indication of why the row is blank.
**Fix:** Render the summary span only when `issue.fields?.summary` is present. Also consider an `aria-label` on the button, e.g. `${issue.key} ${summary}`.

## Info

### IN-01: The search `fields=` string is duplicated in two places

**File:** `src-tauri/src/commands.rs:751` and `src-tauri/src/jira_client.rs:57`
**Issue:** The same long field list is hard-coded twice, and this change had to edit both. They can drift apart.
**Fix:** Extract a shared `const SEARCH_FIELDS: &str` and interpolate it into both URLs.

### IN-02: Mock fixtures hard-code the parent summary and status

**File:** `src-tauri/src/fixtures.rs:1120, 1155, 1199, 1234`
**Issue:** The parent summary and status ("In Progress") are copied as literals instead of being derived from the PROJ-1 fixture. If PROJ-1 changes, the mock parent goes out of sync. In the v2 and v3 variants the `Open` tickets also point at an "In Progress" parent, which is harmless but easy to miss.
**Fix:** Build the parent JSON from a shared helper or constant.
