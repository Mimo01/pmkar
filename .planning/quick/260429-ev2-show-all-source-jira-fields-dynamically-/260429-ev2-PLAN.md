<objective>
Make the source Jira field display dynamic on both the issue detail Overview tab and the copy preview modal source column. Today both surfaces hardcode ~7 fields (status, priority, assignee, reporter, labels, components, fix versions). The source Jira can return 100+ fields including arbitrary custom fields, none of which surface in the UI without a code change.

The goal is to reuse Phase 17 schema discovery (already cached frontend-side via `useSchemaCacheStore` for `('source', null, null)`) and the Phase 20 schema-type discrimination, but add a small **read-only display layer** — the existing renderer registry produces editable controls, which is not what these surfaces need.

Purpose: every Jira field — including newly added customer custom fields — appears automatically. New schema types fall through to a JSON fallback so the app never silently drops data.

Output:
- One shared display formatter (`sourceValueDisplay.tsx`) discriminating on `FieldSchemaType`.
- One shared section component (`AllFieldsSection.tsx`) used by both surfaces.
- OverviewTab and CopyPreviewModal both render the dynamic list.
- Tests covering the formatter (each schema-type variant + the unknown fallback) and the section (filtering + ordering).
</objective>

<rationale>
Reuse, don't rebuild:

- **Phase 17 (Schema Discovery)** already exposes `discover_source_fields` and the `FieldSchema[]` array via `useSchemaCacheStore.loadSchema('source', null, null)`. We piggy-back on that cache — no new Tauri command, no new fetch path. If the cache is empty on mount, we trigger `loadSchema` exactly like FieldMappingSection does. While loading, we render the raw `fields` map with best-effort labels (the field key) so the UI is never blocked.
- **Phase 20 (Renderer Registry)** owns the canonical `FieldSchemaType` union and the discrimination strategy (`schema.type` + `schema.items` + `schema.system` + `schema.custom`). The new `sourceValueDisplay` mirrors that switch shape but emits read-only React nodes — it does NOT extend the registry, since the registry is contract-bound to editable `RendererProps`. Read-only display is a parallel, smaller surface, intentionally.
- **Filtering noise**: drop `null`, `undefined`, `''`, `[]`, `{}`, `workratio === -1`, and any field whose `fieldId` starts with `_` (Jira internal). System fields without a `name` from the schema fall back to the raw key, prettified.
- **Backward compatibility with the editable copy modal**: `AllFieldsSection` only replaces the source-column SourceFieldRow stack (purely read-only). The right-column DynamicTargetForm is untouched — that's Phase 20/22's domain. OverviewTab keeps its bespoke Description / Sub-tasks / Linked Issues sections because those are not flat field rows; the dynamic section sits ABOVE them and covers everything else.

This single plan stays well under ~30% context: ~3 new files (one component, one formatter, two test files) + edits to two existing surfaces + a handful of i18n keys. No backend changes — `fetch_ticket_detail` already requests `fields=*all`.
</rationale>
