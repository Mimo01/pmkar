## Warnings

### WR-01: Group memberships from a previous scope can be pruned against a new scope's tickets

**File:** `src/features/groups/missingMembers.ts:42-55`
**Issue:** The guard checks `groupStore.hydrated`, but `hydrated` stays true across a server switch. `resetForServerSwitch` clears tickets and the signature, then the first complete fetch under the new baseUrl makes `readHintsEligibleNow()` true. If the group store still holds the old scope's `memberKeysByGroup` at that moment (rehydrate not yet finished or failed), every old-scope member is absent from the new tickets and is deleted via `remove_issues_from_group`. This is a data-loss window. The same applies to the key-collision case where the memberships belong to a different scope than the tickets. I did not confirm the ordering of hydrate versus fetch on a switch.
**Fix:** Track the scope the group store was hydrated for, for example a `hydratedScope` set in `load()`. In `pruneMissingMembers`, skip when `hydratedScope !== (serverConnection?.baseUrl ?? '')`. Alternatively set `hydrated=false` when the scope changes and until the rehydrate finishes.

### WR-02: Missing-key set is computed before the await, with no recheck immediately before the invoke

**File:** `src/features/groups/missingMembers.ts:48-53`
**Issue:** `removeFromGroup(id, [...keys])` is awaited with a key list computed just before the call. If a new fetch starts, or a ticket returns, between computing the list and the backend executing it, that ticket is removed anyway. The window is small because the check and the invoke are synchronous up to the IPC boundary. But the backend call is irreversible and there is no backend-side guard. The docs claim eligibility is enforced "at call time", which is true only up to the invoke.
**Fix:** Accept the residual risk and document it, or pass the fetch signature and generation to the backend. Alternatively, run the loop only when `fetchGeneration` is unchanged and re-run if it changed.

### WR-03: Silent failure leaves the effect with no retry and no user signal

**File:** `src/features/groups/missingMembers.ts:50-55`
**Issue:** Failures only `console.warn`. `mutate` calls `hydrate()` on success and on `not_found`, but not on other errors. Memberships stay unchanged, so no dependency changes and no retry happens until the next ticket or fetch change. This is acceptable for self-healing, but a persistent backend error is invisible, and a `console.warn` in production code is a debug artifact.
**Fix:** Use the project's logger if one exists. Accept that the next fetch retries.
